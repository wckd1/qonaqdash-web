## Feature implementation (definition of done)

Treat **new product behavior**, **API integration changes**, and **visible UI changes** the same: complete the full checklist below in the **same change set** when user-facing behavior, contract assumptions, or design authority shift.

**These items are blocking.** Do not treat implementation as finished after "it works locally" alone. Skipping applicable items is a **process failure**, not an optional follow-up.

1. **API contract (`docs/integration.md` + `docs/openapi.yaml`) (MUST)** — **[integration.md](docs/integration.md)** and **[openapi.yaml](docs/openapi.yaml)** are the **source of truth** for wiring with the backend. `openapi.yaml` (OAS 3.0) is the **canonical** reference for every route, request/response shape, field descriptions, examples, and per-endpoint error behaviour; `integration.md` holds **narrative** context (auth flows, forms, grid UX, cross-cutting rules). Implement and parse HTTP **strictly against the contract**: feature `api.ts` files call `typedApi` (`src/shared/api/typed.ts`), which types method, path, path params, query, body and response by the generated `paths`; contract types come from `Schemas['…']` of the same module, not from hand-written interfaces; keep behaviour aligned with **integration** where it adds context. **Do not edit the contract copy (`docs/openapi.yaml`, `docs/swagger.yaml`, `docs/integration.md`) or `src/shared/api/schema.d.ts` by hand**: the backend owns them, and the copy here is refreshed only by `npm run contract:sync` (see [API contract copy](#api-contract-copy)). **Contract gaps go to the work package plan:** record them under «Открытые вопросы» in the local plan (`qonaqdash-docs/work/progress/wp-NN-frontend.md`, see [Work packages](#work-packages)) when **(a)** a required endpoint, payload, or error behaviour is **missing** from the current contract; **(b)** the existing contract shape is **suboptimal** and a better approach is obvious (propose the improvement, don't silently work around it); **(c)** any other contract gap forces the frontend to guess or hack. Include: method and path, what is needed, and how the UI will use it. **Do not paper over contract gaps in silence; do not invent client-side workarounds for missing endpoints.** **Skill (when shaping proposals):** **api-design-principles**.

2. **Page spec & catalog (`docs/design.md`) (MUST for new pages/routes)** — **Before building** a new page: read **[design.md](docs/design.md) → [Page templates](docs/design.md#page-templates)** and **[App screens catalog](docs/design.md#app-screens-catalog)**; pick the **closest existing template** (T1–T7) and reference page. Check **[design.html](docs/design.html)** for shared component markup (buttons, toolbars, panels, tables, dialogs). **Add a catalog row** to `design.md` with: route, view file, template ID, and routine actions/content — **before or while** building the view. Copy the **closest `*.vue` layout** as a starting point, then prune what you don't need. When the page is final, **update the catalog row** with the accurate description. **No new page ships without a catalog entry.** If the task does not introduce a new route, skip this step.

3. **Design authority (`design.html` / `main.css` / tokens) (MUST when UI or product chrome changes)** — **`design.html` + `main.css`** = **design system** (top-level visuals). Align implementation with **`src/assets/main.css`** (shared, feature-agnostic rules only) and **[design.html](docs/design.html)** (visual gallery; mocks not in `main.css` must live in that file's `<style>`). Prefer tokens over ad-hoc colors/sizing. If you change shared patterns or tokens, update **`design.html`** when the gallery should reflect it. Page-specific styles go in the view's **`<style scoped>`**; if a scoped extension appears on another screen, **propose** promoting it into the design system (`main.css` + gallery) per **[design.md → Documentation layers](docs/design.md#documentation-layers)**.

4. **Implementation quality (MUST)** — Match existing feature layout (`src/features/…`, thin stores, feature `api.ts`), shared patterns in `src/shared/`, and the conventions in the sections below. **Vue / Router / Pinia work:** follow **vue-best-practices**; use **vue-router-best-practices** and **vue-pinia-best-practices** when routes or stores are involved. **New reusable composables** whose inputs may be refs or plain values: prefer **create-adaptable-composable**. **Substantial or cross-cutting features:** consider **planning** (structured plan under `docs/plans/` when that skill is invoked); if a plan file exists before build-out, **plan-review** can sanity-check it. **Exploration / options:** **brainstorm** when the user wants design or approach discovery before coding.

5. **i18n (MUST for new or changed user-visible copy)** — Add or update keys in **`src/locales/en.json` and `src/locales/ru.json`**. Do not hardcode new English UI strings. Show server errors through `formatApiError(data.error)`: it localizes by `errors.<code>` and falls back to the server `message` (do not invent English-only fallbacks that hide API messages).

6. **Build and linters (MUST)** — Run **`npm run build`** and fix failures introduced by the change. Run **`npm run lint`** (ESLint) and **`npm run format:check`** (Prettier) — fix any errors or formatting violations in **touched files** before considering the work done. Run **`npm run test`** (Vitest) and add tests for changed logic; see [Tests](#tests). **`npm run ci`** runs typecheck, lint, format check, tests and build in one go, as CI does. Quick reference: `npm run lint:fix` auto-fixes ESLint issues; `npm run format` auto-formats with Prettier. **Debugging Vue/runtime issues:** **vue-debug-guides**. **Automated tests** (when present or added): **vue-testing-best-practices** / **test-automator**.

7. **Task overview (MUST)** — When the task is complete, run **frontend-design** and **interface-design** skills as hard gates when UI was touched (hierarchy, motion, a11y, token/swap/squint/signature tests). **In the same delivery** (assistant response, PR description, or equivalent), include a **short task overview**: what was built/changed, what was verified (build, linters, UI skills, i18n, design.md catalog if applicable), plus gaps or intentional exceptions. **Silently skipping this summary for substantive work is incomplete.**

8. **Learnings (MUST at end of significant changes)** — When the user asks to capture session knowledge (**learn** skill) or at the end of a significant change, update this **AGENTS.md** if something durable about process or architecture was discovered. Do not defer to a later session.

## Architecture

- **Project structure**: Feature-based — `src/features/{auth,billing,bookings,dashboard,employees,guests,pricing,property,tasks}/` each with own views, components, composables and `api.ts` + `queries.ts`; Pinia stores only for the session (`useAuthStore`, `useSettingsStore`); shared code in `src/shared/` (api client, layouts, common components).
- **CSS architecture**: **[design.md](docs/design.md)** defines **layers and where styles live** (_Documentation split_ — design system vs page spec vs app; _CSS placement and naming_; _Page templates_). **Design system:** [design.html](docs/design.html) + [src/assets/main.css](src/assets/main.css) (tokens, typography, cross-route components: app shell, lists, side panels, dialogs, search, `.action-toolbar`, status chips, form banners, …); gallery adds **doc `<style>`** for mocks **not** in `main.css`. **Implementation:** **`*.vue` `<style scoped>`** for genuine one-offs; **propose** promoting to `main.css` (+ gallery when useful) when a second screen shares the pattern, then refactor. **Recurring `main.app-main > …`** list/form patterns stay in **main.css**. **Home grid** toolbar + `dashboard-view__*`: **`DashboardView.vue`**. Prefer explicit **`__viewport`** class names; use **`:deep()`** when adjusting children. Use tokens, not ad-hoc hex/rgba/rem.
- **Token storage & refresh**: Access and refresh JWTs live in **localStorage** (`access_token`, `refresh_token`); **`useAuthStore`** mirrors them. **Refresh is implemented:** on **401** with API error code **`common.jwt_expired`**, the Axios client performs a **single-flight** `POST /api/auth/refresh` with the stored refresh token via **`refreshTransport`** (no JWT interceptors on that client), persists the new pair, then **retries the failed request once**. Login/invite routes and **`PUT /api/account`** (wrong password) do not trigger refresh. **Planned (WP6, decision D10):** sessions in the backend DB with the refresh token in an **httpOnly cookie**, so no `refresh_token` in localStorage or request body. Known bug **F1** (a reload with an expired access token deletes a live refresh token) is pinned by a `test.fails` in `src/router/index.test.ts`.
- **API client**: Axios with interceptors (JWT, 401 redirect, errors). **Exception:** `PUT /api/account` may return **401** for a wrong current password while the session stays valid — do **not** clear tokens or redirect to login; treat similar endpoints the same way if they appear. **Permissions refresh:** on any **403**, show the toast, keep the user in context, and refresh the cached account/permissions snapshot in the background so nav and action gating can recover after role changes.
- **Feature API modules**: Each feature has its own `api.ts` (e.g. `src/features/auth/api.ts`) for HTTP and parsing, and a `queries.ts` that wraps it in Pinia Colada queries and mutations (see [Server state](#server-state-pinia-colada)); views use the queries, not `api.ts` directly. **Contract types are generated** (`src/shared/api/schema.d.ts`, never written by hand): each feature `api.ts` names the ones it uses as aliases of `Schemas['…']` (e.g. `export type Hotel = Schemas['propertyhttp.HotelResponse']`), so views import them from `@/features/…/api`. Shared code that needs a contract type uses `Schemas['…']` directly. UI-only types (FormDSL data shapes, filters) live next to the code that owns them.
- **Employees feature**: Follow the same runtime FormDSL pattern as guests/bookings: feature-local `api.ts` + `queries.ts` in `src/features/employees/`, cached `GET /api/employees/form?target=…`, builder route at `/manage/forms/employees`, and list → side panel → full detail navigation. Employee profile now also carries a **special access-settings section** (occupations + permission overrides + effective-permissions preview) when the actor has `hotel.manage_permissions`; occupation templates live under **Hotel → Occupations** (`/manage/hotel/occupations`) and use the shared permission matrix UI. For role-family metadata, use **`GET /api/occupations/role-groups`** as the create-time source of truth; empty groups are intentional and let the frontend render all valid role families.
- **API integration**: Endpoint details live in **[openapi.yaml](docs/openapi.yaml)**; narrative integration rules in **[integration.md](docs/integration.md)**. If the backend should change shape or add endpoints/params to support the frontend properly, say so explicitly (what to return, why). Do not paper over gaps in silence. **Record every proposed backend change under «Открытые вопросы» in the current package plan** (method and path, what is needed, how the frontend will use it).

## Server state (Pinia Colada)

Server data lives in the Pinia Colada query cache (decision D14), not in Pinia stores. Pinia stores keep only UI state and the session (tokens, locale, the cached permissions snapshot for route guards).

- **Where:** each feature keeps its queries and mutations in `queries.ts` next to its `api.ts`. `api.ts` stays plain HTTP and parsing; `queries.ts` adds keys, caching and invalidation.
- **Keys:** `[feature, kind, ...params]`, built only by the feature's key factory (`bookingKeys`, `guestKeys`, …), e.g. `['bookings', 'list', { q }]`, `['bookings', 'detail', id]`, `['bookings', 'grid', { from, to }]`. Params are plain JSON (objects, not refs). `['bookings']` matches every bookings entry and `['bookings', 'detail']` every detail, so invalidation can target a whole feature or kind.
- **Queries:** define options once with `defineQueryOptions` in `queries.ts` and use them in views as `useQuery(() => bookingDetailQuery(id.value))`. The query function passes `signal` to axios, so a superseded or cancelled request is aborted. Use `enabled` for permission or missing-param gates, `placeholderData: (prev) => prev` where a list keeps its rows while a new search loads.
- **Mutations:** `useXxxMutation()` composables in `queries.ts` wrap `useMutation`. On success they update or invalidate every key whose data the request changed, including keys of other features (a check-out also changes tasks, rooms and the folio). Views do not refetch by hand after a mutation.
- **Reading outside components:** route guards and the API client use `useQueryCache()` (`queryCache.fetch(queryCache.ensure(options))`).
- **No hand-made loading state:** no "already loaded" flags, no `mutateAndRefresh` chains, no sequence counters for stale responses. Loading and errors come from `isPending`, `asyncStatus` and `error` of the query.
- **Defaults** (`src/shared/api/queryCache.ts`): `staleTime` 5 s and `gcTime` 5 min from Pinia Colada; no refetch on window focus or reconnect, so a background refetch cannot replace data under a form being edited. Edit forms copy query data into local state once.
- **Logout** calls `clearServerState()` (`src/shared/api/queryCache.ts`): it drops every cached entry, so the next user never sees the previous user's data.
- **Form definitions** keep their own hash cache (`src/shared/forms/loadRuntimeFormDefinition.ts`, reworked in WP7); queries call it like any other API function.
- **Unit tests:** `setupColada()` from `src/test-utils/colada.ts` gives a fresh Pinia with Pinia Colada and runs composables in the app context.

## Work packages

Work is planned in `qonaqdash-docs/work/`: a PM session writes briefs, and the backend and frontend agents work on them in parallel. Process and hand-off format: `qonaqdash-docs/work/README.md`; accepted decisions: `qonaqdash-docs/work/decisions.md`.

- Each package has a sealed brief `wp-NN-<slug>.md` (goal, scope, API changes, order, shared acceptance criteria) and a branch `wp-NN-<slug>` with the same name in every repository, cut from `main`. Agents never edit the brief.
- The frontend tasks, details and progress of a package live in the local plan `qonaqdash-docs/work/progress/wp-NN-frontend.md`. It is not committed (`work/progress/` is in `.gitignore` of the docs repository).
- Do only what the brief and the plan cover. Anything found outside them goes to «Находки вне скоупа» of the plan, not into code.
- Contract gaps and product or UX questions the brief does not answer go to «Открытые вопросы» of the plan, with options and a recommendation. Keep working on the rest.
- Code against the API changes described in the brief, not against an unfinished backend branch. On the integration step, run `npm run contract:sync` from the package branch of `../qonaqdash`, fix mismatches and run e2e against the live backend.
- The frontend agent writes only its plan: «Открытые вопросы», «Находки вне скоупа», «Передача», «Интеграция». Re-read the file before every edit.
- No push, no merge into `main`, no history rewrites of shared branches. The PM does that after the owner's OK.

## API contract copy

`docs/openapi.yaml` (OAS 3.0, canonical), `docs/swagger.yaml` (its Swagger 2.0 source) and `docs/integration.md` are a committed copy of the backend contract (decision D2). They are never edited by hand.

- `npm run contract:sync` copies the three files from the backend checkout, writes `docs/contract.lock` (backend commit, branch, sync time, whether the backend contract files had uncommitted changes, and a SHA-256 of each copy) and regenerates the API types. Commit the copy, the lock and the types together.
- `npm run api:types` regenerates `src/shared/api/schema.d.ts` from `docs/openapi.yaml` with `openapi-typescript` (decision D13), formatted with Prettier. The file is committed and never edited by hand.
- `npm run contract:check` fails when a copy differs from the backend checkout, does not match the lock (edited by hand), or `schema.d.ts` is not what `api:types` generates from the copy. It needs the backend checkout, so CI does not run it.
- `openapi-typescript` 7 declares `typescript@^5` as a peer; `overrides` in `package.json` points it at the project TypeScript 6, which its AST printer works with.
- The backend checkout defaults to `../qonaqdash`. Set `QONAQDASH_BACKEND_DIR` (absolute or relative to this repository) to use another one. The scripts only read it.

## Commits

- The message is in English and starts with a past-tense verb: `Added`, `Fixed`, `Updated`, `Changed`, `Removed`, `Moved`, `Renamed`, `Reworked`, and so on.
- A commit is atomic: one feature or one change. Unrelated changes go to separate commits.
- Every commit keeps `npm run build` green.
- Two related changes in one commit get a two-line message, each line starting with a verb, with no blank line between them.
- No body, except rare cases where important context is not visible from the diff.
- No `Co-Authored-By` or other attribution lines.

## Conventions

- **Shared components**: Reused UI → `src/shared/` (or appropriate shared path). Keep components token-driven; move duplicated layout from features into `main.css` when it becomes a system pattern.
- **`docs/`**: Design, and the copy of the backend contract: **high-level API integration** ([integration.md](docs/integration.md)), **OpenAPI** ([openapi.yaml](docs/openapi.yaml), with its Swagger 2.0 source [swagger.yaml](docs/swagger.yaml)) and `contract.lock`; excluded from app builds. The contract files change only through `npm run contract:sync`. Files under `docs/` **should** cross-link each other when helpful. Do **not** reference `docs/*.md` / `docs/*.html` paths inside `src/` comments or JSDoc — contracts stay in docs; application code stays self-contained. Procedural pointers to which doc is which remain in this file for agents.
- **Markdown**: Do not create `.md` files unless the user asks.
- **Quality**: Fix root causes; avoid workaround-only fixes.
- **API errors**: Backend returns `{ "error": { "code", "message", "fields"?, "issues"? } }` (`sharedhttp.ErrorResponse` / `sharedhttp.APIError` in the contract). `code` is the stable id (`common.*`, `booking.*`, …); `message` is an English fallback. Show errors through `formatApiError(data?.error)` / `formatUnknownApiError(err)` from `src/shared/i18n/apiError.ts`; validation errors (`common.validation_failed` issues, and a `400`/`422` with `fields`) map to form fields through `formErrorsMapFromHttpError`. `FormEdit` shows an error next to its field when a shown control has that bind; form-level errors and errors of binds no shown control displays (a hidden field, a field the form does not have, an array itself, a row field the server reports without the row) go to the alert above the form (`formRootErrors`), so no error is lost. On guest, booking and employee `POST`/`PUT` the API client shows no toast for these errors (`422 common.validation_failed`, `400` with non-empty `fields`); a `400` without `fields` still gets a toast.

## Frontend / Vue

- **Pinia in views**: Use `storeToRefs(store)` when destructuring store state so async updates stay reactive.
- **Property data**: hotel, room types, rooms and availability come from `src/features/property/queries.ts`. A search `q` is part of the key, so a filtered list never replaces the full one that other screens read.
- **Form templates**: runtime forms are queries: guest `guestRuntimeFormQuery` (per `_form.hash` of `GET /api/guests/:id`) and `guestCreateFormQuery`; booking `bookingDetailQuery` (aggregate + runtime form per target, from `fetchBookingWithRuntimeForm`) and `bookingCreateFormQuery`; the stored quote of a booking is the separate `bookingQuoteQuery` (`src/features/pricing/queries.ts`), so a role that may read the booking but not its quote still opens it; employee likewise. The loader keeps the hash-based disk+memory cache (`src/shared/forms/formDefinitionCache.ts`, `qonaqdash-docs/forms-caching.md`, reworked in WP7). Saving a definition in the builder clears that cache and invalidates the feature's keys. Runtime `GET …/form` responses include `hash`; detail payloads include `_form: { id, hash }`. **Create guest/booking/employee:** every open sends `GET …/form?target=edit` with `If-None-Match: "<last hash>"` when known (the hash in the create-form query entry); `304` keeps cached definition, `200` refreshes after backend form changes (`loadRuntimeFormDefinition`).
- **Guest/booking lists**: The search text is part of the list query key, so every search is its own cache entry and the full list is never replaced by a filtered one.
- **Router**: Catch-all under main layout for 404 inside shell. **Static routes before dynamic** (e.g. `guests/new` before `guests/:id`). Dashboard/home link: **`router-link-exact-active`** when all routes nest under `/`, so home is not active on every page.
- **Pico**: Margin overrides and new Pico tweaks go in `main.css`. Input outline: `--pico-outline-width` is `0.0625rem` on inputs vs `0.125rem` on root — match custom controls (e.g. search) to inputs.
- **Naming**: Views named for the **screen** (`RoomsView` not `PropertyView` for rooms). Management/admin routes under **`/manage/`**.
- **Accordions**: Native `<details>` without controlled `:open` when multiple independent open sections are desired.
- **Lists with search**: Match Guests pattern: server `q`, debounce, `initialLoading` vs `searching`, spinner in search bar. Record API gaps under «Открытые вопросы» in the current package plan. Prefer server-side search, not client-only filtering.
- **List layout**: Search always under page header; below that — error, loading, or content (never hide search on error/empty).
- **Page layout**: `app-layout` → `app-layout-body` → `sidebar` + `main.app-main` with `router-view` in `main`. Each page: `header.page-header` then siblings with `gap: var(--space-md)`. **Lists**: `search` then `section.list-content` (`overflow: hidden`, `position: relative`); scroll in **`list-content__viewport`**; **side panel sibling after** viewport (not inside it). **Forms**: `form-content__viewport` inside FormDSL components (`FormEdit` / `FormView` / `FormBuild`). **Home / grid** (`DashboardView.vue`): root `.dashboard-view` (flex column); scroll in **`dashboard-view__viewport`**; content toolbar markup + styles are **scoped in the view** (not `main.css`); `design.html` duplicates toolbar CSS under `.ds-content-toolbar-preview` for reference. **Guest detail**: `.guest-detail-body` scroll; form + bookings order per `GuestDetailView` / `:deep` rules. **404**: `.not-found` in `main`. `main.app-main` stays `position: relative` for overlays.
- **Avoid extra wrappers**: No redundant wrapper around search. No extra top-level section when the form definition already sections content. **Keep** intentional scroll roots: `list-content__viewport`, `dashboard-view__viewport` (home grid), `form-content__viewport`, `guest-detail-body`, `guest-detail-form`.
- **FormDSL (runtime UI)**: **`src/shared/form-dsl/`** — `FormEdit`, `FormView`, `FormBuild`; `edit` / `view` / `build` renderers (`LayoutRenderer`, `ControlRenderer`, `ArrayRenderer`); `utils.ts`, `formNodeConditions.ts`, `validateFormData.ts`. Payloads use the API's snake_case keys; guest is flat, booking is `{ guest, stay, adjustments? }`. Field bindings use dot-path `bind` on definition nodes. No top-level `id` on create/update — `guest.id` only. Guest and employee writes and their edit forms use only profile fields: `guestProfileFields` / `employeeProfileFields` drop the keys the server owns (`id`, `blocked`, `_form`, and for employees the access settings). Detail: Save then Cancel (`.btn-secondary`); Cancel on detail only. **Types:** FormDSL node types and `FormRef` in **`src/shared/form-dsl/types.ts`**; booking and guest form data shapes in **`src/features/bookings/api.ts`** and **`src/features/guests/api.ts`**.
- **FormDSL conditions / actions**: `formNodeConditions.ts` evaluates `visibleWhen` / `hiddenWhen` / `enabledWhen` / `disabledWhen` against form data. Button `actions` run in edit mode. Pass **root** data as **`fullData`** into nested `ControlRenderer` when conditions reference guest-scoped binds.
- **Form route height**: `main.app-main--fit-content` on short form/settings routes (new entity, profile, manage forms, hotel); **guest/booking full detail** fills main height (default flex) with inner scroll on `.guest-detail-body` (and booking form viewport as needed). Flex + `min-height: 0` on the active scroll root. **Modals**: `Teleport` to `body`; `.dialog-backdrop` / `.dialog` are global in `main.css` because `container-type: inline-size` on `main` would otherwise make `position: fixed` cover only `main`.
- **HorizontalLayout / builder**: `.form-view-layout--horizontal` children flex; `.form-view-layout__fields` grid; builder `.form-build-shell` spans full grid width. `FormBuild`: max two children per horizontal row; group title behavior for `main` / `field_*` ids per `resolveGroupTitle`.
- **Date-time**: Store RFC 3339; `datetime-local` in UI with conversion in ControlRenderer.
- **Composables**: If returning `{ ref, ref }`, wrap with `reactive()` so templates see unwrapped booleans/arrays, not Ref objects.
- **i18n**: Keys in `src/locales/{en,ru}.json`; `useI18n` / `$t` in components; `i18n.global.t` in non-SFC helpers. New/changed UI strings → both locale files. `page_title.*` / router for titles; detail views may set `document.title` from loaded data. Do not hardcode English for server errors; use `formatApiError`. RU: product-appropriate wording, not literal only. In script, don't shadow `t` from `useI18n()`.
- **Account / locale**: `GET`/`PUT /api/account` per **[openapi.yaml](docs/openapi.yaml)** and **[integration.md](docs/integration.md)**. The account is the `accountQuery` in `src/features/auth/queries.ts`; every load also calls `useSettingsStore().applyAccount()`, which updates the cached **effective permissions** snapshot (localStorage, for route guards and chrome gating) and sets the locale from the account only when the locale is not pinned. `refreshAccount()` forces a load after login, invite, authenticated `App` mount, a change of the user's own permissions, and on a 403 (permission-staleness recovery). Sidebar name and email come from the account query, then the JWT. Use the shared permission helpers/composable instead of ad-hoc `resource.action` checks inside views.
- **Hints**: Secondary copy under labels: `--text-caption-size`, `--text-caption-weight`.
