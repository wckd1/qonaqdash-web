## Feature implementation (definition of done)

Treat **new product behavior**, **API integration changes**, and **visible UI changes** the same: complete the full checklist below in the **same change set** when user-facing behavior, contract assumptions, or design authority shift.

**These items are blocking.** Do not treat implementation as finished after "it works locally" alone. Skipping applicable items is a **process failure**, not an optional follow-up.

1. **API contract (`docs/integration.md` + `docs/swagger.yaml`) (MUST)** — **[integration.md](docs/integration.md)** and **[swagger.yaml](docs/swagger.yaml)** are the **source of truth** for wiring with the backend. `swagger.yaml` is the **canonical** reference for every route, request/response shape, field descriptions, examples, and per-endpoint error behaviour; `integration.md` holds **narrative** context (auth flows, forms, grid UX, cross-cutting rules). Implement and parse HTTP **strictly against Swagger**; keep behaviour aligned with **integration** where it adds context. **Do not edit `docs/integration.md` or `docs/swagger.yaml` in this repo** (backend owns them). **Backend change requests — record in [backend-change-requests.md](docs/backend-change-requests.md) when:** **(a)** a required endpoint, payload, or error behaviour is **missing** from the current contract; **(b)** the existing contract shape is **suboptimal** and a better approach is obvious (propose the improvement, don't silently work around it); **(c)** any other contract gap that forces the frontend to guess or hack. Include: method/path, params, reason, and how the UI will use it. **Do not paper over contract gaps in silence; do not invent client-side workarounds for missing endpoints.** Follow **[backend-change-requests.md](docs/backend-change-requests.md)**: backend marks **`[x]`** and fills **Done** (Swagger / integration pointers); after the **frontend** ships against that handoff, **remove the whole request block** so the queue stays accurate. **Skill (when shaping proposals):** **api-design-principles**.

2. **Page spec & catalog (`docs/design.md`) (MUST for new pages/routes)** — **Before building** a new page: read **[design.md](docs/design.md) → [Page templates](docs/design.md#page-templates)** and **[App screens catalog](docs/design.md#app-screens-catalog)**; pick the **closest existing template** (T1–T7) and reference page. Check **[design.html](docs/design.html)** for shared component markup (buttons, toolbars, panels, tables, dialogs). **Add a catalog row** to `design.md` with: route, view file, template ID, and routine actions/content — **before or while** building the view. Copy the **closest `*.vue` layout** as a starting point, then prune what you don't need. When the page is final, **update the catalog row** with the accurate description. **No new page ships without a catalog entry.** If the task does not introduce a new route, skip this step.

3. **Design authority (`design.html` / `main.css` / tokens) (MUST when UI or product chrome changes)** — **`design.html` + `main.css`** = **design system** (top-level visuals). Align implementation with **`src/assets/main.css`** (shared, feature-agnostic rules only) and **[design.html](docs/design.html)** (visual gallery; mocks not in `main.css` must live in that file's `<style>`). Prefer tokens over ad-hoc colors/sizing. If you change shared patterns or tokens, update **`design.html`** when the gallery should reflect it. Page-specific styles go in the view's **`<style scoped>`**; if a scoped extension appears on another screen, **propose** promoting it into the design system (`main.css` + gallery) per **[design.md → Documentation layers](docs/design.md#documentation-layers)**.

4. **Implementation quality (MUST)** — Match existing feature layout (`src/features/…`, thin stores, feature `api.ts`), shared patterns in `src/shared/`, and the conventions in the sections below. **Vue / Router / Pinia work:** follow **vue-best-practices**; use **vue-router-best-practices** and **vue-pinia-best-practices** when routes or stores are involved. **New reusable composables** whose inputs may be refs or plain values: prefer **create-adaptable-composable**. **Substantial or cross-cutting features:** consider **planning** (structured plan under `docs/plans/` when that skill is invoked); if a plan file exists before build-out, **plan-review** can sanity-check it. **Exploration / options:** **brainstorm** when the user wants design or approach discovery before coding.

5. **i18n (MUST for new or changed user-visible copy)** — Add or update keys in **`src/locales/en.json` and `src/locales/ru.json`**. Do not hardcode new English UI strings. Server `data.error` stays as returned (do not invent English-only fallbacks that hide API messages).

6. **Build and linters (MUST)** — Run **`npm run build`** and fix failures introduced by the change. Run **`npm run lint`** (ESLint) and **`npm run format:check`** (Prettier) — fix any errors or formatting violations in **touched files** before considering the work done. Quick reference: `npm run lint:fix` auto-fixes ESLint issues; `npm run format` auto-formats with Prettier. **Debugging Vue/runtime issues:** **vue-debug-guides**. **Automated tests** (when present or added): **vue-testing-best-practices** / **test-automator**.

7. **Task overview (MUST)** — When the task is complete, run **frontend-design** and **interface-design** skills as hard gates when UI was touched (hierarchy, motion, a11y, token/swap/squint/signature tests). **In the same delivery** (assistant response, PR description, or equivalent), include a **short task overview**: what was built/changed, what was verified (build, linters, UI skills, i18n, design.md catalog if applicable), plus gaps or intentional exceptions. **Silently skipping this summary for substantive work is incomplete.**

8. **Learnings (MUST at end of significant changes)** — When the user asks to capture session knowledge (**learn** skill) or at the end of a significant change, update this **AGENTS.md** if something durable about process or architecture was discovered. Do not defer to a later session.

## Tech Stack

- **Frontend**: Vue 3 + TypeScript + Vite + Pinia + Vue Router + Pico CSS (`vue-tsc` in build)
- **Backend**: Go modular monolith, REST JSON API, JWT auth (HS256)

## Architecture

- **Project structure**: Feature-based — `src/features/{auth,property,guests,bookings}/` each with own views, stores, composables; shared code in `src/shared/` (api client, layouts, common components).
- **CSS architecture**: **[design.md](docs/design.md)** defines **layers and where styles live** (_Documentation split_ — design system vs page spec vs app; _CSS placement and naming_; _Page templates_). **Design system:** [design.html](docs/design.html) + [src/assets/main.css](src/assets/main.css) (tokens, typography, cross-route components: app shell, lists, side panels, dialogs, search, `.action-toolbar`, status chips, form banners, …); gallery adds **doc `<style>`** for mocks **not** in `main.css`. **Implementation:** **`*.vue` `<style scoped>`** for genuine one-offs; **propose** promoting to `main.css` (+ gallery when useful) when a second screen shares the pattern, then refactor. **Recurring `main.app-main > …`** list/form patterns stay in **main.css**. **Home grid** toolbar + `dashboard-view__*`: **`DashboardView.vue`**. Prefer explicit **`__viewport`** class names; use **`:deep()`** when adjusting children. Use tokens, not ad-hoc hex/rgba/rem.
- **Token storage & refresh**: Access and refresh JWTs live in **localStorage** (`access_token`, `refresh_token`); **`useAuthStore`** mirrors them. **Refresh is implemented:** on **401** with API error code **`common.jwt_expired`**, the Axios client performs a **single-flight** `POST /api/auth/refresh` with the stored refresh token via **`refreshTransport`** (no JWT interceptors on that client), persists the new pair, then **retries the failed request once**. Login/invite routes and **`PUT /api/account`** (wrong password) do not trigger refresh. **Hardening (optional / backend-dependent):** moving the refresh token to an **httpOnly cookie** would still require backend support and client changes (no `refresh_token` in localStorage or request body).
- **API client**: Axios with interceptors (JWT, 401 redirect, errors). **Exception:** `PUT /api/account` may return **401** for a wrong current password while the session stays valid — do **not** clear tokens or redirect to login; treat similar endpoints the same way if they appear. **Permissions refresh:** on **403** with `common.forbidden`, show the toast, keep the user in context, and refresh the cached account/permissions snapshot in the background so nav and action gating can recover after role changes.
- **Feature API modules**: Each feature has its own `api.ts` (e.g. `src/features/auth/api.ts`) for HTTP and parsing; stores stay thin and call these modules. **Shared domain / contract types** live in **`src/shared/types/`** (e.g. `bookings.ts`, `guests.ts`, `property.ts`, `auth.ts`); feature `api.ts` files **re-export** those types so existing `import type { … } from '@/features/…/api'` continues to work.
- **Employees feature**: Follow the same runtime FormDSL pattern as guests/bookings: feature-local `api.ts` + thin Pinia store in `src/features/employees/`, cached `GET /api/employees/form?target=…`, builder route at `/manage/forms/employees`, and list → side panel → full detail navigation. Employee profile now also carries a **special access-settings section** (occupations + permission overrides + effective-permissions preview) when the actor has `hotel.manage_permissions`; occupation templates live under **Hotel → Occupations** (`/manage/hotel/occupations`) and use the shared permission matrix UI. For role-family metadata, use **`GET /api/occupations/role-groups`** as the create-time source of truth; empty groups are intentional and let the frontend render all valid role families.
- **API integration**: Endpoint details live in **[swagger.yaml](docs/swagger.yaml)**; narrative integration rules in **[integration.md](docs/integration.md)**. If the backend should change shape or add endpoints/params to support the frontend properly, say so explicitly (what to return, why). Do not paper over gaps in silence. **Record every proposed backend change in [backend-change-requests.md](docs/backend-change-requests.md)** (method/path, params, reason, how the frontend will use it).

## UI and UX

- **Design system**: [design.html](docs/design.html) + `main.css` define top-level visuals; [design.md](docs/design.md) specifies pages using that naming; views add scoped extensions and propose promotion when patterns repeat (see _Documentation split_).
- **Navigation**: Dark collapsible sidebar — Dashboard, Bookings, Guests; **Management** group (Hotel, Pricing, guest/booking forms, Reports under `/manage/…`). Footer: Profile → `/profile`, Log out. Tokens: `--sidebar-bg`, `--sidebar-text`, `--sidebar-user-menu-bg`, etc. **Permissions drive composition**: sidebar items, management links, subnav tabs, and action buttons are hidden when the cached effective-permissions bundle does not allow them; direct navigation to blocked routes goes to the in-shell **403** page. **Hotel** sidebar item covers `/manage/hotel`, `/manage/hotel/occupations`, and `/manage/rooms` via `PropertySubNav`; sidebar highlights on any of those paths. **Guests/Bookings** nav highlights exclude `/manage/guests` and `/manage/bookings` so form editors don't highlight list items. **Management** group: closed by default; auto-open only on first load if URL is under `/manage/`, or when entering `/manage/` from outside — not on every hop between manage routes. Narrow rail: Management trigger hidden; manage links as icons.
- **Interaction pattern**: List or grid → side panel (summary + quick actions) → full page (detail + edit) for bookings and guests.
- **Visual direction**: Cool gray-blue canvas, teal accent (`--brand-primary`); corporate but joyful; generous whitespace. Body: Inter; display: Manrope (Latin + Cyrillic). Content area uses `--content-area-gap`, `--content-area-radius`.
- **Booking status colors**: `--status-confirmed`, `--status-checked-in`, `--status-checked-out`, `--status-canceled`.
- **Dashboard grid**: Reservation timeline in `ReservationGrid.vue`. Presets 7/14/30: `localStorage` + `/?from=&to=`. Preset range: **forward-biased** (`from` = yesterday, `to` = today + (n−2)) so **today is the 2nd column**; custom dates still allowed. `DashboardView` content toolbar (scoped CSS): preset `.toolbar-picker`, From/To `.toolbar-input`, **`@change` reloads** (no Apply); primary `.toolbar-btn` reapplies current preset from "now".
- **Bookings vs dashboard**: Grid uses `GET /api/bookings/grid`; Bookings **list** uses `GET /api/bookings` (with `q`). List: row → panel → full detail.
- **Reservation grid behavior**: Room-type bands use tokens (e.g. `color-mix` on `--control-bg` / `--ink-primary`). Keep range highlight while cell context menu is open. **New booking from cells**: multi-day → check-in first day 14:00, check-out last day 12:00; single day → one night, check-out next day 12:00. Dashboard nav icon: layout-dashboard (grid), not a house.

## Conventions

- **Shared components**: Reused UI → `src/shared/` (or appropriate shared path). Keep components token-driven; move duplicated layout from features into `main.css` when it becomes a system pattern.
- **`docs/`**: Design, **high-level API integration** ([integration.md](docs/integration.md)), **OpenAPI** ([swagger.yaml](docs/swagger.yaml)), and the change-request queue live here; excluded from app builds. Files under `docs/` **should** cross-link each other when helpful. Do **not** reference `docs/*.md` / `docs/*.html` paths inside `src/` comments or JSDoc — contracts stay in docs; application code stays self-contained. Procedural pointers to which doc is which remain in this file for agents.
- **Markdown**: Do not create `.md` files unless the user asks.
- **Quality**: Fix root causes; avoid workaround-only fixes.
- **API errors**: Backend uses `{ "error": "human-readable message" }`. Surface `data?.error`, not `data?.message`, in the client and views.

## Design System Notes

- **Intent** (in `main.css` header): reception/staff, bookings/guests, warm calm teal. New tokens should match that intent.
- **Content / forms**: Full-width content sections; vertical form stacks; labels per global `label` rule. Input/select/textarea value size: **`--text-label-size`** (checkbox/radio excluded); compact toolbars may override locally.
- **UI review**: Same bar as **Feature implementation (definition of done)** step 7 — **frontend-design** / **interface-design**; component fallbacks match tokens; avoid layout that fights full-width content; token names should read as product-specific.

## Frontend / Vue

- **Pinia in views**: Use `storeToRefs(store)` when destructuring store state so async updates stay reactive.
- **Pinia — property lists**: `usePropertyStore` idempotently hydrates full `fetchRoomTypes` / `fetchRooms` via flags (not `array.length`). Non-empty `q` clears **both** flags (search can return partial lists).
- **Pinia — form templates**: Guest: `_form.hash` on `GET /api/guests/:id` keys hash-based runtime cache (`src/shared/forms/formDefinitionCache.ts`, `docs/forms-caching.md`); Pinia slots `guestFormTemplate` / `guestFormRuntimeView` hold the last loaded snapshot; `replaceGuestFormTemplate` invalidates disk+memory runtime cache. Booking: same pattern with `fetchBooking` + `loadBookingRuntimeForm`; create flow keeps `bookingFormTemplate` for edit until invalidated. Runtime `GET …/form` responses include `hash`; detail payloads include `_form: { id, hash }`. **Create guest/booking:** every open sends `GET …/form?target=edit` with `If-None-Match: "<last hash>"` when known (`guestCreateFormHash` / `bookingCreateFormHash`); `304` keeps cached definition, `200` refreshes after backend form changes (`loadRuntimeFormDefinition`).
- **Guest/booking lists**: No session skip-cache for list fetches — search and filters break a single "full list" invariant.
- **Router**: Catch-all under main layout for 404 inside shell. **Static routes before dynamic** (e.g. `guests/new` before `guests/:id`). Dashboard/home link: **`router-link-exact-active`** when all routes nest under `/`, so home is not active on every page.
- **Pico**: Margin overrides and new Pico tweaks go in `main.css`. Input outline: `--pico-outline-width` is `0.0625rem` on inputs vs `0.125rem` on root — match custom controls (e.g. search) to inputs.
- **Naming**: Views named for the **screen** (`RoomsView` not `PropertyView` for rooms). Management/admin routes under **`/manage/`**.
- **Accordions**: Native `<details>` without controlled `:open` when multiple independent open sections are desired.
- **Lists with search**: Match Guests pattern: server `q`, debounce, `initialLoading` vs `searching`, spinner in search bar. Document API gaps in [backend-change-requests.md](docs/backend-change-requests.md). Prefer server-side search, not client-only filtering.
- **List layout**: Search always under page header; below that — error, loading, or content (never hide search on error/empty).
- **Page layout**: `app-layout` → `app-layout-body` → `sidebar` + `main.app-main` with `router-view` in `main`. Each page: `header.page-header` then siblings with `gap: var(--space-md)`. **Lists**: `search` then `section.list-content` (`overflow: hidden`, `position: relative`); scroll in **`list-content__viewport`**; **side panel sibling after** viewport (not inside it). **Forms**: `form-content__viewport` inside FormDSL components (`FormEdit` / `FormView` / `FormBuild`). **Home / grid** (`DashboardView.vue`): root `.dashboard-view` (flex column); scroll in **`dashboard-view__viewport`**; content toolbar markup + styles are **scoped in the view** (not `main.css`); `design.html` duplicates toolbar CSS under `.ds-content-toolbar-preview` for reference. **Guest detail**: `.guest-detail-body` scroll; form + bookings order per `GuestDetailView` / `:deep` rules. **404**: `.not-found` in `main`. `main.app-main` stays `position: relative` for overlays.
- **Avoid extra wrappers**: No redundant wrapper around search. No extra top-level section when the form definition already sections content. **Keep** intentional scroll roots: `list-content__viewport`, `dashboard-view__viewport` (home grid), `form-content__viewport`, `guest-detail-body`, `guest-detail-form`.
- **FormDSL (runtime UI)**: **`src/shared/form-dsl/`** — `FormEdit`, `FormView`, `FormBuild`; `edit` / `view` / `build` renderers (`LayoutRenderer`, `ControlRenderer`, `ArrayRenderer`); `utils.ts`, `formNodeConditions.ts`, `validateFormData.ts`. Payloads camelCase; guest flat, booking `{ guest, booking }`. Field bindings use dot-path `bind` on definition nodes. No top-level `id` on create/update — `guest.id` only. Detail: Save then Cancel (`.btn-secondary`); Cancel on detail only. **Shared API / form shapes:** **`src/shared/types/bookings.ts`**, **`src/shared/types/guests.ts`**, **`src/shared/types/forms.ts`**; feature **`api.ts`** files re-export those types for convenience.
- **FormDSL conditions / actions**: `formNodeConditions.ts` evaluates `visibleWhen` / `hiddenWhen` / `enabledWhen` / `disabledWhen` against form data. Button `actions` run in edit mode. Pass **root** data as **`fullData`** into nested `ControlRenderer` when conditions reference guest-scoped binds.
- **Form route height**: `main.app-main--fit-content` on short form/settings routes (new entity, profile, manage forms, hotel); **guest/booking full detail** fills main height (default flex) with inner scroll on `.guest-detail-body` (and booking form viewport as needed). Flex + `min-height: 0` on the active scroll root. **Modals**: `Teleport` to `body`; `.dialog-backdrop` / `.dialog` are global in `main.css` because `container-type: inline-size` on `main` would otherwise make `position: fixed` cover only `main`.
- **HorizontalLayout / builder**: `.form-view-layout--horizontal` children flex; `.form-view-layout__fields` grid; builder `.form-build-shell` spans full grid width. `FormBuild`: max two children per horizontal row; group title behavior for `main` / `field_*` ids per `resolveGroupTitle`.
- **Date-time**: Store RFC 3339; `datetime-local` in UI with conversion in ControlRenderer.
- **Composables**: If returning `{ ref, ref }`, wrap with `reactive()` so templates see unwrapped booleans/arrays, not Ref objects.
- **i18n**: Keys in `src/locales/{en,ru}.json`; `useI18n` / `$t` in components; `i18n.global.t` in non-SFC helpers. New/changed UI strings → both locale files. `pageTitle.*` / router for titles; detail views may set `document.title` from loaded data. Do not hardcode English for server `data.error`. RU: product-appropriate wording, not literal only. In script, don't shadow `t` from `useI18n()`.
- **Account / locale**: `GET`/`PUT /api/account` per **[swagger.yaml](docs/swagger.yaml)** and **[integration.md](docs/integration.md)**; `useSettingsStore.fetchUserSettings()` after login, invite, authenticated `App` mount, and permission-staleness recovery; `setLocale` from account only when locale not pinned; sidebar email from account then JWT. The same store now caches the authenticated user's **effective permissions** in localStorage for route guards and chrome gating; use the shared permission helpers/composable instead of ad-hoc `resource.action` checks inside views.
- **Hints**: Secondary copy under labels: `--text-caption-size`, `--text-caption-weight`.
